Native Bundle quick start

Use the verified Native Bundle for your operating system. Its commands and state are separate from the legacy Wheel client.

  1. Verify the official delivery with the independent verifier and follow the included installation guide.
  2. For an existing installation, preserve its identity and state; check status before continuing.
  3. For a new Paid device, use register and the Native portal. Convert an existing Native Trial with paid on that same installation.
  4. Confirm the valid signed Lease and test Gateway → Core → Protected Handler before opening production traffic.

Existing Wheel installation guide

Die Wheel-Befehle odre-pqc-commercial activate/deactivate sind keine Native-Kundenbefehle. Übertragen Sie keinen Wheel-Zustand auf Native. Gerätewechsel und Serverumzüge benötigen derzeit Prüfung und Freigabe durch den Support. Der veröffentlichte Launcher bietet keinen selbstständigen Transfer. Eine Neuregistrierung überträgt keine vorhandene Unit. Wählen Sie ausdrücklich Transfer oder zusätzliche freie Unit. Starten Sie keine neue Trial als Ersatz für einen Transfer.

  1. Offizielles Bundle verifizieren und installieren; Abhängigkeiten prüfen.
  2. Nur bei Neuinstallation: odre-pqc init.
  3. odre-pqc doctor ausführen.
  4. odre-pqc verify ausführen (unabhängiger Core-Selbsttest).
  5. In main.py Core mit install(app) registrieren, dann Gateway und Commercial gate anbinden; Identity, Trust und geschützte Routen konfigurieren.
  6. Trial aktivieren oder bei bezahlter Lizenz odre-pqc-commercial activate und Web-Freigabe abschließen.
  7. odre-pqc-commercial status prüfen; bei bezahlter Aktivierung ACTIVE, LEASE_VALID, integrity PASS und Unit-Zuweisung bestätigen.
  8. Kundenserver und Gateway private Core starten.
  9. odre-pqc status für den vorgesehenen laufenden Core ausführen.
  10. Gateway → Core → Protected Handler einschließlich fail-closed per Smoke-Test prüfen; nicht mit Core-Selbsttests verwechseln.
  11. Production-Traffic erst nach Bestehen aller zutreffenden Gates freigeben.
Release-Manifest-Signatur → artifact SHA-256 prüfen → erst nach PASS installieren. Der veröffentlichte v0.2.9-Core-Wheel-Hash ist eine Core-Referenz, nicht der Hash des endgültigen Commercial + Gateway + Core Bundles.

Verification & known limitation

Installation

The commands in this section apply to existing Wheel installations. For Native Bundle, follow the dedicated installation guide. View Native guide

Vor der Installation die Signatur des Release Manifest und den SHA-256 des offiziellen Bundles prüfen, anschließend die Abhängigkeiten kontrollieren. Das bereitgestellte Commercial + Gateway + Core Bundle und dessen Installationsanleitung verwenden.

  1. Windows Server 2022 AMD64 oder Ubuntu 24.04 LTS AMD64 sowie CPython 3.12 bestätigen.
  2. Vor der Installation die Signatur des Release Manifest und den SHA-256 des offiziellen Bundles prüfen, anschließend die Abhängigkeiten kontrollieren. Das bereitgestellte Commercial + Gateway + Core Bundle und dessen Installationsanleitung verwenden.
  3. Release-Manifest-Signatur → artifact SHA-256 prüfen → erst nach PASS installieren. Der veröffentlichte v0.2.9-Core-Wheel-Hash ist eine Core-Referenz, nicht der Hash des endgültigen Commercial + Gateway + Core Bundles.
  4. odre-pqc init nur einmal bei einer Neuinstallation ausführen. Bei Updates oder erneuter Installation vorhandene Konfiguration, Schlüssel und Zustand beibehalten. Vor dem Serverstart zuerst odre-pqc doctor, dann odre-pqc verify ausführen. Verify ist ein unabhängiger Core-Selbsttest, kein Test Ihrer Gateway-Integration.
  5. ODRE PQC importieren, die Core-Grenze mit install(app) registrieren und danach Gateway und Commercial gate in main.py anbinden. Gateway-Identity, Schlüssel, Trust, geschützte Routen und startup/shutdown konfigurieren. Die Core-Registrierung allein schließt die Integration nicht ab. Das zutreffende Trial- oder kostenpflichtige Aktivierungsverfahren abschließen und den Commercial status prüfen. Server und private Core starten, den Status des laufenden Core prüfen und Gateway → Core → Handler per Smoke-Test verifizieren, bevor Traffic freigegeben wird.

Production-Integration

The commands in this section apply to existing Wheel installations. For Native Bundle, follow the dedicated installation guide. View Native guide

Der bestätigte Einstiegspunkt für die Core-Registrierung ist bewusst klein gehalten:

from fastapi import FastAPI
from odre_pqc import install

app = FastAPI()
install(app)
Dieser Code registriert nur die Core-Grenze. Für den Production-Einsatz sind zusätzlich Gateway und Commercial gate des Kunden-Bundles sowie Identity-, Key-, Trust-, Routen-, Start- und Shutdown-Konfiguration erforderlich.

odre-pqc verify ist ein unabhängiger Core-Selbsttest. Er weist nicht den laufenden Pfad Gateway → Core → Protected Handler nach; führen Sie vor Freigabe geschützten Traffics den releasespezifischen Smoke-Test durch.

Lizenzzustellung

Bei einem regulären Paddle-Kauf wird die beim Checkout angegebene E-Mail über den signierten Zahlungsablauf erneut geprüft und zur Lizenzzustellung verwendet. Die Browser-Rückkehrseite allein gilt nicht als Zahlungsnachweis.

License ID und License Key aus der Zustellmail können auf der sicheren Aktivierungsseite serverseitig geprüft werden. Gerätebindung und Ausgabe der Offline Lease erfolgen im installierten ODRE PQC.

Betrieb & Updates

Status

The commands in this section apply to existing Wheel installations. For Native Bundle, follow the dedicated installation guide. View Native guide

odre-pqc status fragt authentifizierte Runtime-Nachweise eines laufenden Core ab, keine verify-Ergebnisdatei. Erst nach dem Start ausführen. Ein erfolgreicher Core status belegt allein weder Gateway private Core noch die Integration Gateway → Core → Handler; dafür ist ein separater Smoke-Test erforderlich.

Verify

The commands in this section apply to existing Wheel installations. For Native Bundle, follow the dedicated installation guide. View Native guide

odre-pqc verify führt unabhängige kryptografische Core-Selbsttests mit temporären Schlüsseln und einer temporären DB aus, darunter ML-KEM-768 und ML-DSA-65. Bei der Installation ausführen; nicht als Nachweis der kundenseitigen FastAPI/Gateway-Integration werten oder zu diesem Zweck wiederholen.

Betrieb

Normales Herunterfahren stoppt neue geschützte Annahmen, beendet laufende Arbeit begrenzt, verwirft Sitzungen und Leases, schließt native Ressourcen, gibt Sperren frei und protokolliert den gestoppten Zustand. Die Absturzwiederherstellung prüft Eigentum, veraltete Sperren, Sitzungen und teilweise initialisierte Runtime vor der Rückkehr zu Ready.

Update

Verifizierte Updates verwenden den unterstützten Aktualisierungspfad. Schlägt ein sicherer Abschluss fehl, wird die aktive Version nicht umgeschaltet.

Problemlösung

Doctor

Diagnostiziert Betriebssystem, Architektur, Python-Runtime, Datei- und Elternberechtigungen, Hashes, Symbole, Provider, Abhängigkeiten und Zugriff auf lokalen Zustand. Eine ungelöste Bedingung blockiert geschützten Verkehr.

Fehlerbehebung

  • Hashabweichung: Installation stoppen und das Artefakt erneut über den offiziellen Lieferweg beziehen.
  • Nicht unterstütztes Betriebssystem, Architektur oder Python-Version: Umgebung nicht als verifiziert bezeichnen; vor der Bereitstellung technischen Support kontaktieren.
  • doctor- oder verify-Fehler: geschützten Verkehr deaktiviert lassen, bis die gemeldete Bedingung behoben ist.
  • Lizenzmail fehlt: nicht erneut kaufen; Wiederherstellung oder Lizenz-Support nutzen.
  • Nicht öffentlich abgedeckte Betriebsanweisungen: den mit dem Release gelieferten Kundenleitfaden verwenden.
