Security

A defined security boundary with a defined verification scope.

Review the cryptographic profile, request controls, trust assumptions and limitations of the current release.

Cryptographic profile

The v0.2.9 audited runtime uses OpenSSL 3.5.8 with ML-KEM-768 for key encapsulation and ML-DSA-65 for digital signatures. The published evidence covers actual algorithm self-tests and the product's authenticated hybrid handshake on the two verified platforms.

Session protection and request validation

The protected-route contract includes authenticated session establishment, strict sequence validation, replay rejection, route and session binding, and protection of request meaning. Protected response status, selected headers, cookies and body are carried within the protected response boundary described by the public technical material.

  • Replay and duplicate sequence attempts are rejected.
  • Cross-route, cross-session and method/query substitution are within the published test scope.
  • Invalid, ambiguous or oversized inputs do not become successful protected requests.
  • The handler-observed protected request meaning is bound to the authenticated request meaning.

Fail-closed behavior

If the provider, key material, session, sequence state, native trust state, authenticated status or required runtime condition cannot satisfy the product contract, the protected handler is not treated as successfully protected. The product does not silently continue with classical-only protection for protected routes.

Fail-closed applies to the ODRE PQC protected-route boundary. It does not mean the product replaces host hardening, identity, authorization, TLS, monitoring or application security.

Threat boundary

The public v0.2.9 evidence covers network tampering, replay and concurrency, malformed input, meaning confusion, response metadata exposure, crash and restart state, local file replacement, symbolic-link or reparse manipulation, dependency/provider injection and lifecycle races within its documented configurations.

The assessment assumes the base operating system, CPU, Python runtime and privileged administrator are not fully compromised. A malicious kernel, unrestricted administrator control, physical extraction, application logic defects after admission, unbounded denial of service and future cryptanalytic breaks are not claimed as prevented.

Scope and limitations

  • Published PASS results apply only to the identified artifact, configurations, threat model and executed tests.
  • Verification evidence is not a guarantee against every attack and does not replace deployment risk assessment.
  • Only Windows Server 2022 AMD64 and Ubuntu 24.04 LTS AMD64 with Python 3.12 are identified as verified environments for v0.2.9.
  • Other operating systems, architectures, Python versions, frameworks and deployment patterns are not part of the published verification scope unless separately documented.
